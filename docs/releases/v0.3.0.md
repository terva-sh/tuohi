# tuohi v0.3.0

This source release adds reading an image from the system clipboard, and fixes
two macOS behaviours that Kuiske found with v0.2.0. Existing APIs and their
defaults are unchanged. Go 1.26 remains the minimum; shipped code builds with
`CGO_ENABLED=0`.

```sh
go get github.com/terva-sh/tuohi@v0.3.0
```

## New API

- [Clipboard images](../../clipboard/clipboard.go):
  `clipboard.PasteImage(clipboard.ImageLimits{MaxBytes, MaxPixels})` returns
  the clipboard's image as PNG. It reads an image offered as PNG, BMP, JPEG or
  GIF (the first frame), preferring PNG, decodes it in Go and encodes it
  again, so the result always decodes and carries none of the source's
  metadata. `ErrNoImage` means nothing readable is offered;
  `ErrImageTooLarge` means a limit was exceeded, and its message gives sizes,
  never contents. A zero limit takes its default: 32 MiB and 50 million
  pixels.
  - It is for an image the page's paste event does not carry. WebKitGTK hands
    a page no BMP, which is how WSLg offers an image copied on Windows.
  - BMP is decoded by tuohi, because gdk-pixbuf's BMP loader is optional
    since 2.42.11. The decoder reads the header versions, palettes, bit
    depths and bitfields clipboards carry, and refuses run-length and
    embedded compression.
  - The pixel limit is checked from the image's header, before any pixel is
    decoded. GTK 4 stops reading at the byte limit. **GTK 3 receives the whole
    transfer first**, so there the byte limit bounds what is kept and
    decoded, not what GTK buffers for the call.
  - **macOS and Windows return `ErrUnsupported`.** They are follow-up work.

Clipboard reads on GTK, `Paste` and `PasteImage` alike, wait for the process
that owns the clipboard with no timeout of their own. An owner that never
answers keeps the call waiting, so a caller with a deadline runs them from a
goroutine it can abandon. The documentation now says so; a cancellable
variant is follow-up work.

## Fixes

- macOS supplements the menu commands a bundled launch's placeholder main
  menu leaves out: the Edit actions through the responder chain, and Close
  and Quit, without replacing the host's menus or actions. Quit goes through
  `App.Quit`, so the caller can join teardown; Close keeps the normal window
  policy.
- macOS `View.Hide` on a fullscreen window waits for AppKit to finish leaving
  fullscreen, so hiding no longer leaves a black dedicated Space. The window
  and its renderer are retained. Repeated hides coalesce, and a reveal, close
  or quit cancels a pending hide.

## Validation and limits

`PasteImage` has headless tests for the decoder and limits, and GUI scenarios
on both WebKitGTK stacks under Xvfb. Those put real images on a real X11
clipboard from a separate owner process: PNG, WSLg's `text/html` and
`image/bmp` offer, text only, both limits, and an image the process offers
itself. On a Wayland session the scenarios read only the process's own offer,
because a compositor gives the clipboard to a focused client only.

On the owner's WSLg machine (Windows build 26200, WSL 2.7.11, WSLg 1.0.73,
Ubuntu 24.04, WebKitGTK 2.52.6, Wayland), pasting an image copied in a
Windows browser into Kuiske at `debc890` opened Kuiske's preview. Which
WebKitGTK stack that run used was not recorded. A tuohi probe there read a
Wayland `image/bmp` offer on GTK 3.

The macOS fixes have native synthetic regressions in tuohi. Kuiske's own
isolated macOS acceptance of the same behaviour preceded moving them here.
The [desktop acceptance record](../desktop-acceptance.md) lists what remains
open since v0.2.0:
interactive packaged macOS notifications, production signing and bundle
replacement, and tray usability on macOS, WSLg and Steam Frame. This release
does not claim those passed.

Known open problems, not fixed here: WebKitGTK 4.1 2.54.0 can crash on an
allowed read of an unowned X11 clipboard; an older WebView2 runtime
occasionally dropped a `data:` page's binding message; and Windows never
applies the default background colour, because tuohi asks WebView2 for
`ICoreWebView2Controller2` with the wrong IID.
