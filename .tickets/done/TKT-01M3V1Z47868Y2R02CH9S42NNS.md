## Description

### What

On Windows, App.Wait with App.Exit set sometimes does not return after the last window is closed with View.Close from a goroutine. closeFromGoScenario (close_wait_test.go, from TKT-01M3N0PTS10TG629DVNEFSNVSZ) reports "Wait did not return after View.Close from a goroutine" until its 30 s watchdog calls App.Quit.

### Evidence

- GitHub run 36822261007 (main at 16ee80a, PR #60): passed on Windows.
- GitHub run 36822614924 (main at 4895e32, PR #61): failed on Windows.
- GitHub run 36823983447 (main at 2e2a7c3, the revert of #61): failed on Windows. So the failure does not depend on #61's code.

### Where to look

The close path looks complete on reading. View.Close off the UI thread posts destroyOnUI to the window. WM_DESTROY calls appWindowClosed, then requestExit, then appUIWake, which posts WM_QUIT to uiThreadID(). appUIWait returns on WM_QUIT, and Wait sees the exit flag. Candidates:
- A nested message pump swallowing that WM_QUIT. `embed` returns an error on WM_QUIT without re-posting it, unlike `installDocScript`.
- Ready firing while Show is still pumping, before Wait runs, so the close and its WM_QUIT land inside a nested pump.
- uiThreadID being captured on the wrong thread (TKT-01M3N0PTR5E1NP8TT9XV07GBTK).

The scenario's WEBVIEW2_DEBUG trace in those runs is the first thing to read. Adding a trace line in appUIWake and appUIWait would settle which one it is.

## Acceptance criteria

- [x] The cause of the missed close is found and recorded
- [x] TestWaitReturnsAfterCloseFromGo passes on 20 consecutive Windows runs

## Implementation plan

GitHub run 36827912989 reported windows=-1 exit=0 at the hang. A window from an earlier scenario closed late: its teardown waited in the message queue until the next App's Show pumped it. appWindowClosed decremented scopePtr, the most recent scope, so the count went 0 -> -1 before our window was counted, and our close then took it from 0 back to -1. It never reached zero, so requestExit never ran. Fix: each viewCore records the scope that counted its window (viewCore.scope, set in showFirst), and the engines call reportClosed, which reports to that scope at most once (atomic Swap). appWindowClosed is gone. Rejected: guarding the count against going negative, which would hide which scope a close belongs to, and draining stale closes before Show, which cannot know which messages are stale.

## Summary

App.Wait missed a Close from Go on Windows for two reasons, both fixed: a window's close was reported against the newest App scope instead of its own (#66, viewCore.reportClosed), and View.Close's Terminate posted a quit outside Run that later killed the next window's creation (#67, webview.running). 20 consecutive Windows passes on GitHub.
