## Description

GitHub native run 39869664509 at desktop integration merge c7c7681 failed TestAcquireSendRoundTrip: Send returned success but no forwarded message arrived within ten seconds. notify/tray/updater passed; later Windows examples/WebView2 steps were skipped. macOS, all Linux jobs, builds and lint passed.

The server currently handles ConnectNamedPipe ERROR_NO_DATA by disconnecting without attempting to read. Microsoft documents this status when a client has already closed its pipe handle. A small write can be buffered and its client closed before the server goroutine calls ConnectNamedPipe; DisconnectNamedPipe then discards unread data. Drain the closed client through the existing bounded reader rather than discard it. Add a deterministic native regression that completes Send before starting the server loop, preserving ACLs, owner checks, byte limits, deadlines, cancellation and subsequent connections.

References: https://github.com/terva-sh/tuohi/actions/runs/39869664509/job/120140627295 ; https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-connectnamedpipe ; https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-operations . Native Windows execution is unavailable locally; cross-compilation alone is not confirmation. Fix under the owner-authorized merge/native-regression follow-through; no version publication.

## Implementation plan

Separate pipe allocation from serving so a native test can deterministically complete a small Send and close before the server loop begins. Treat ERROR_NO_DATA from ConnectNamedPipe as a closed client to drain through the unchanged bounded reader, then disconnect and continue serving. Verify exact message delivery plus subsequent delivery, keep the existing security/size/stall/release suite, run cgo-free CI and all cross builds, and request fresh full PR review. Native Windows results come from the mirror after merge; do not infer them from compilation. Reject a startup sleep, unbounded FlushFileBuffers, retrying Send blindly (duplicate risk), and protocol changes because draining already-buffered bytes preserves compatibility and shutdown bounds.
